# ADR：Harness のコアの形（共通は User scope、プロジェクトならではは Project scope）

> **読む前に**：この ADR は、その日の相談の順に書いた記録で、用語の統一（[2026-11-08-terminology.md](2026-11-08-terminology.md)）より前の言葉（オーナー＝Boss、参謀長＝Orchestrator、作業者＝Worker、監査＝Reviewer、見張り＝Guard など）のまま残しています。途中の案のうち、次の3つはあとで改めました。
> - 「記録は別の非公開リポジトリに置く」→ **各プロジェクトの `team/` に置く**（下の「続けて決めたこと・したこと」）
> - 「今の状況は `NOW.md`」→ **`team/STATUS.md`**
> - 「SNS はハーネスのフォルダで開く」→ **SNS も専用のプロジェクトのフォルダで開く**
>
> 現在の形は、README と `rules/operations.md` が正です。

- 日付：2026-11-08
- 決めた人：Boss
- 記録した人：Orchestrator

## 決めたこと

共通の部分は根に近い所に、アプリならではの決まりは各アプリのフォルダに置く。3段にする。

| 段 | 場所 | 置くもの |
|---|---|---|
| ① 共通の入り口 | `C:\Users\user\.claude\` | 見張りのつなぎ、秘密を読ませない設定、作業者・監査の役、最初に読む短い指示書 |
| ② ハーネス本体 | `harness/` | 決まりの本文、書式、見張りのプログラム、テスト |
| ③ アプリならでは | 各アプリ | `.claude/harness.json`（検査・push の決まり）、アプリの CLAUDE.md |

- 見張りは、`.claude/harness.json` があるフォルダでだけ、アプリの決まり（検査・push）を使う。
- 参謀長を開く場所は、そのとき進める仕事に合わせる（開発はアプリ、SNS などはハーネス）。どこで開いても守りは同じ。

## 理由

- オーナーは「開発と SNS を同時に進める」「アプリが増えても柔軟に」をしたい。入り口と守りを1つにしたい。
- Claude Code が設定を読むのは、開いたフォルダとユーザーの場所だけ。足したフォルダの設定（見張り）は読まれない（公式の資料）。
- アプリごとに写す形は、ずれる（実践記事でも、写しのずれを検査で見張る手間が報告されている）。

## 検討したほかの案

- アプリで開く（今の形）：入り口がアプリの数だけでき、設定を写す手間がある。
- 本部（ハーネス）だけで開く：作業場所が自動でアプリに作れない。

## 影響する範囲・次にやること

- ユーザー全体の設定は、この PC の Claude Code のすべての使い方に効く（ハーネスと関係ない作業でも、一括削除などは止まる）。
- 次に決める：リポジトリを「公開する仕組み」と「非公開の記録」に分けるか、同時並行の決まり。

## 続けて決めたこと（同じ日）

- **リポジトリを2つに分ける**：仕組み（決まり・見張り・書式。いずれ公開）は `harness`、記録（依頼・タスク・監査・報告・見張りの記録）は別の非公開のリポジトリ。公開するときに、自分の記録や住所が漏れないようにするため。
- **同時並行の決まり**：
  1. 1つのアプリを触る会話は1つまで（同じファイルを2つの会話が同時に書いて壊れた、という実践記事の失敗例があるため）
  2. 「今の状況」は会話（受け持ち）ごとに分ける
  3. 書いてよいのは自分の受け持ちの記録だけ。ハーネスの決まりを変えるのは参謀長だけ
  4. 副参謀長は、オーナーが2つ目のタブを開いて「あなたは〇〇担当の副参謀長」と言うと立つ。報告はオーナーに直接出す（参謀長を通すと受け渡しが増えるため）

## 続けて決めたこと・したこと（同じ日、組み直し）

- **プロジェクトの記録は、そのプロジェクトの中で完結させる**（オーナー）：記録は各プロジェクトの `team/`。ハーネスはチームの頭脳（仕組み）だけになり、そのまま公開できる。これで「記録用の別リポジトリ」は要らなくなった。SNS も1つのプロジェクトとして専用のフォルダを持つ。
  - 作業場所はプロジェクトまるごとの写しなので、中の `team/` も写しになる。記録は必ず本体の `team/` に書き、見張りが写しへの書き込みを止める。
- 第三者の点検（別の AI に、こちらの結論を渡さずに読ませた）と、実践記事 16 本を受けて、見張りを作り直した：
  - 抜け道（`bash -c`・`$( )`・`xargs`・`find -exec`・シェルに流すヒアドキュメント・`cd` で外へ出る・`node -e` で書く・`git -c`・`update-ref`・`push --delete`）をふさいだ
  - 知らない名前の役は、いちばん弱い権限にした（前は参謀長と同じだった）
  - 取り込み（`git merge`）の前に、監査に合格した記録があるかを確かめるようにした
  - 秘密の読み取り（`~/.ssh`・Cloudflare や Expo のログインの情報）と、中身が本番の操作のスクリプト（`pnpm deploy` など）を足した
  - 作業者・監査・知らない役のすべての操作を、見張りの記録に残すようにした（`team/logs/`、git に入れない）
  - 監査は、判定を書き終えてから作業報告を読む（作る側の言い分に引っぱられないため）
- 日報と承認票の一覧はやめた（だれも書いていなかった）。事後報告は報告か `team/NOW.md` に、承認票はプロジェクトの `team/approvals/` に置き、フォルダの中身が一覧になる。（Boss に伝え、異論が出なかったので、この形で確定とする）
- 見張りの正直な限界：文字でコマンドを読むので、「うっかり」は防げるが、すべての抜け道はふさげない。外側の守り（GitHub の main の保護、バックアップ）をオーナーに頼んだ。

## 見直す時期

作業者と監査を、この形で一度動かしたあと。
